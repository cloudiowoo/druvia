# Data Access 生成列能力修复设计及实施方案

状态：本地实施、验证与高风险 review 已完成，等待 PITCHETCH 应用侧验收
Owner：Druvia Data Access
日期：2026-09-05

## 1. 背景

PITCHETCH 项目表 `dru_default_pitchetch.capture_observation` 包含 PostgreSQL
`GENERATED ALWAYS` 列。Druvia 当前将同一组全量列同时用于 Hasura select、insert 和
update permission，导致生成列进入 `insert_permission.columns`，Hasura 拒绝 metadata
更新并使管理 API 返回 HTTP 502。

该缺陷同时影响单表策略保存、策略反向识别、项目 overview 和 Data Access migration
的 preview/apply/rollback/recover，不能通过针对单表名称或单个路由的特殊处理解决。

## 2. 目标与非目标

### 2.1 目标

1. 以 PostgreSQL 列属性建立 readable、insertable、updateable 三组内部能力。
2. 生成列和 `IDENTITY ALWAYS` 列可读，但不得进入 Hasura insert/update permission。
3. `IDENTITY BY DEFAULT` 和普通 default 列保持可写。
4. owner insert 仅允许 Hasura preset 可以写入的 owner 列。
5. policy materialization 与 metadata inspection 使用同一能力模型。
6. overview 和 Data Access migration 全链路使用一致能力模型。
7. 保持现有管理 API 的 `columns` 返回字段兼容。
8. 服务端记录脱敏的 Hasura metadata 错误上下文，客户端继续返回通用错误。

### 2.2 非目标

- 不修改 PITCHETCH 业务 schema 或 generated expression。
- 不直接修改 Hasura metadata 绕过 Druvia。
- 不改变 Project User、API Key、平台用户或 Hasura role 的身份语义。
- 不增加新的数据库 migration。
- 不把数据库列级权限编辑能力开放到管理界面。

## 3. 方案与决策

### 3.1 仅排除 generated columns

改动最小，但无法正确表达 `IDENTITY ALWAYS`，并会继续把 insert/update 两种能力混为
一谈。

结论：拒绝。

### 3.2 使用统一 writableColumns

可以解决当前表，但无法为 PostgreSQL 或 Hasura 后续出现的操作级差异保留明确契约。

结论：拒绝。

### 3.3 操作级列能力

采用内部 `DataAccessColumnCapabilities`：

```ts
interface DataAccessColumnCapabilities {
  readableColumns: string[]
  insertableColumns: string[]
  updateableColumns: string[]
}
```

规则如下：

| 列属性 | readable | insertable | updateable |
| --- | --- | --- | --- |
| 普通列，包括普通 default | 是 | 是 | 是 |
| `GENERATED ALWAYS AS (...)` | 是 | 否 | 否 |
| `GENERATED ALWAYS AS IDENTITY` | 是 | 否 | 否 |
| `GENERATED BY DEFAULT AS IDENTITY` | 是 | 是 | 是 |

能力由 `information_schema.columns.is_generated`、`is_identity` 和
`identity_generation` 决定，不使用对 generated column 仍可能返回 `YES` 的
`is_updatable` 作为唯一依据。

结论：采用。

## 4. 数据流设计

### 4.1 元数据读取

- `table.service.ts` 的单表元数据查询增加 generated/identity 属性，并将能力传给单表
  Data Access 上下文。
- `data-access-inventory.ts` 在一次 inventory 查询中分别聚合三种有序列集合。
- 对外 `TableDataAccessState.columns` 继续返回 `readableColumns`，不改变 Admin 契约。

### 4.2 策略生成与识别

- select 和 anonymous select 使用 `readableColumns`。
- insert 使用 `insertableColumns`。
- update 使用 `updateableColumns`。
- owner insert 从 insertable columns 排除 owner，并使用 Hasura `set` 写入 owner。
- owner update 从 updateable columns 排除 owner，禁止客户端转移所有权。
- 任意 owner 模式要求 owner column 存在；owner insert 额外要求 owner column 可 insert。
- inspection 对每种 operation 使用对应列集合，保证平台生成的 metadata 能重新识别为
  managed。

### 4.3 Migration 兼容

- 新 migration table snapshot 持久化三种列集合，并将 plan contract 升级为 version 2。
- 新字段进入 snapshot digest，升级前尚未 apply 的 preview 因 source drift 必须重新生成。
- migration 消费 snapshot 时对历史 version 1 记录做读取时兼容，缺失能力时回退为原有
  全量列语义，仅用于读取历史记录及必要的 rollback/recover。
- version 1 digest 比较使用移除新增能力字段的旧形状；version 2 digest 包含完整能力字段。
- 新 preview、target snapshot 和 verifier 一律使用 operation-specific capabilities。

### 4.4 错误处理与日志

- `DataAccessValidationError` 继续映射为 HTTP 400。
- Hasura metadata 错误继续对客户端映射为脱敏 HTTP 502。
- API 使用 Fastify request logger 记录 request ID、project、schema、table、operation 和
  脱敏后的 Hasura code/message；不记录请求头、token、permission 行值或凭据。

## 6. 验收标准

1. `capture_observation` 的四个 generated columns 出现在 select permission，但不出现在
   insert/update permission。
2. `insert: owner` 为 `user_id` 设置 preset，客户端 columns 不包含 `user_id`。
3. generated 或 Identity Always owner column 用于 owner insert 时返回 HTTP 400。
4. 合法 generated-table permission 被 inspection 识别为 managed。
5. overview 返回 `read_write` 且 `reviewRequired=false`。
6. 普通表现有 permission 输出不变。
7. migration preview/apply/rollback/recover 和 verifier 使用一致列能力。
8. 旧 migration 记录可读取；升级前未应用 preview 不会绕过新能力直接 apply。
9. Hasura 上游错误可通过 request ID 定位，客户端不暴露敏感详情。
10. PITCHETCH 重新应用策略后 `verify-data-access.sh` 通过。

### 7.2 真实环境

本地 PostgreSQL 17/PostGIS 17 与 Hasura v2.48 隔离 fixture 验证通过：

- Generated Always 出现在 select，不出现在 insert/update。
- Identity Always 不出现在 insert/update。
- Identity By Default 保留 insert/update。
- owner insert 通过 `set` 写入普通 owner 列，客户端不能覆盖 owner。
- generated owner insert 在 metadata 写入前返回 validation error。
- 保存后单表 inspection 返回 managed。
- 项目 overview 返回 `read_write`、匿名 `read`、`reviewRequired=false`。
- 测试完成后随机 project、tenant、user、schema 和 Hasura tracking 均已清理，残留计数为 0。

既有全 migration integration 在列权限阶段之后因本地 Realtime JWT 配置返回 WebSocket
`4403` 而中止；该环境问题不属于本修复，失败 fixture 已按 migration 019 状态约束清理。

### 7.3 Review 结论

高风险 review 首轮发现并修正两项问题：

- 共享错误序列化统一脱敏 Bearer/Basic、JSON secret/token、敏感键值和 URL userinfo，

### 7.5 表列表状态后续修复

PITCHETCH 完成业务表配置后，项目“数据表”列表仍将所有 tracked table 显示为“待配置访问”。
根因不是 permission 写入失败，而是 schema status controller 未结合授权 guard 已解析的
`projectAccess.projectId` 和项目当前 `data_access_mode` 选择实际运行时角色；service 因而只
检查旧 `user / anonymous`，没有识别 explicit 项目的 scoped roles。

最终修复按以下边界判断状态：

- controller 从可信 `request.projectAccess` 读取项目，`compatibility` 只检查
  `user / anonymous`，`explicit` 只检查项目 scoped roles；两套角色不做 OR 合并，避免旧
  metadata 让当前运行模式产生假阳性。
- 非默认环境 schema 不复用生产 scoped role；在环境 actor 身份尚未实现前返回
  `environment_identity_required`，Admin 显示“环境访问暂不可用”。
- service 仅在内部读取 Hasura `select_permissions.role`，对外状态响应不返回物理 role 名称。
